QA-инженер. Тестирует то, что **просили**, поэтому работает по спецификации, а не по коду.

| | |
|---|---|
| Имя | `web-pipeline:qa-engineer` |
| Модель / effort | sonnet / medium |
| Инструменты | Все инструменты сессии |
| Навыки | [`testing-standards`](../skills/testing-standards.md) |
| Кто вызывает | [D3](../delivery.md#d3-задачи-плана) параллельно с реализацией; исправления e2e в [review-loop](../../dev-core/skills/review-loop.md) |
| Stop-gate | При `SubagentStop` хук запускает `make check` ([подробнее](../hooks.md#stop-gate)) |
| Исходник | `plugins/web-pipeline/agents/qa-engineer.md` |

## Процесс

1. Прочитать критерии приёмки в `docs/spec.md` или документе изменения, маршруты и API-контракт. Реализацию для выбора проверок **не читать**.
2. Если Playwright не настроен, настроить: конфиг, `BASE_URL` из окружения, мобильный (375 px) и десктопный проекты, трейсы при падении, тег `@smoke` для smoke-прогона при деплое.
3. Минимум один тест на каждый критерий, с именем `AC-x.y <поведение>`. Только доступные селекторы. Покрыть основной путь, ошибку валидации, границы авторизации и мобильный viewport.
4. Запустить тесты на локальном приложении. Падение, показывающее, что приложение не выполняет критерий, — это **находка**, а не тест, который надо подогнать. Она описывается с AC id, шагами, ожидаемым и фактическим результатом.
5. `make check`.

## Отчёт

- тесты по критериям (соответствие AC → тест);
- результаты pass и fail;
- находки для исполнителей;
- критерии, которые не удалось протестировать, и почему.

## Почему не по коду

Тест, написанный по реализации, проверяет то, что сделано, а не то, что требовалось. Поэтому qa-engineer стартует, как только есть контракт и критерии приёмки, и не ждёт готового кода.
