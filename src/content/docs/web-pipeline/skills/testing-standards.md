## Когда срабатывает

> Testing standards for this user's web projects - TDD per task, test pyramid, behavior-focused tests, integration with real services, Playwright e2e from acceptance criteria, flakiness policy. Load when writing or reviewing tests.

## Порядок работы

- **TDD на каждую задачу:** падающий тест на критерий, самый простой проходящий код, рефакторинг на зелёных тестах.
- Исправление бага начинается с теста, который его воспроизводит.
- Код в унаследованной области перед изменением получает **характеризационный тест**, фиксирующий текущее поведение.

## Пирамида

| Уровень | Что покрывает | Инструменты | Правила |
|---|---|---|---|
| Unit | Чистые доменные правила, утилиты | vitest/jest, pytest | Быстро, без сети, БД и часов (часы внедряются) |
| Integration | Service + repo + реальная БД, HTTP-обработчики | testcontainers или docker compose, supertest/httpx | Реальный движок БД, никогда SQLite вместо Postgres; изоляция транзакцией или truncate |
| Contract | Ответы соответствуют OpenAPI | schemathesis или openapi-валидаторы | На реальном приложении |
| E2E | Пользовательские сценарии из критериев приёмки | Playwright | Немного, только критичные пути; мобильный и десктопный viewport |

## Хорошие тесты

- Проверяют **поведение через публичные интерфейсы**, а не детали реализации. Рефакторинг без изменения поведения не ломает тесты.
- Arrange, Act, Assert, одно поведение на тест. Имя по поведению: `rejects_expired_coupon`, а не `test_coupon_3`.
- Фабрики или билдеры для данных, а не гигантские общие фикстуры.
- Моки только на границах системы: сторонние API, почта, платежи. Своё не мокается ради удобства.
- Никаких snapshot-тестов для логики. Snapshot допустим только для небольшого стабильного сериализованного вывода.
- E2E используют доступные селекторы (`getByRole`, `getByLabel`), никогда CSS-классы или nth-child.

## E2E по спецификации

- Один или больше тестов Playwright на каждый критерий приёмки, с id критерия в имени: `test('AC-1.2 …')`.
- Пишутся по спецификации **до чтения реализации**.
- Минимум: основной путь, одна ошибка валидации, граница авторизации (если применимо), мобильный viewport 375 px.

## Покрытие и нестабильность

- Покрытие — сигнал, а не цель: ≥ 80% строк для domain и service, на склеечном коде не гнаться.
- Нестабильный тест — это баг. Исправить или поместить в карантин с записью в `TODO.md` в рамках той же задачи. Никаких «повторять до зелёного» и `sleep` вместо правильного ожидания.
- Нельзя пропускать, удалять или ослаблять тест ради зелёной проверки, не сказав вам.
