## Когда срабатывает

> Backend engineering standards for this user's web projects - DRY/KISS/YAGNI/SOLID applied pragmatically, reuse-first, contract-first APIs, validation, error model, data access, security baseline, observability and the tools that enforce them. Load for backend design, implementation or review.

## Перед каждым модулем

Протокол [`dev-core:reuse-first`](../../dev-core/skills/reuse-first.md): проект → стандартная библиотека или фреймворк → поддерживаемая библиотека → свой код. `reuse:`-заметка в отчёте.

## Принципы

- **KISS:** самый простой дизайн, удовлетворяющий критериям приёмки. Никаких спекулятивных слоёв, систем плагинов и generic-репозиториев «на будущее».
- **DRY по правилу трёх:** абстрагировать на третьем повторе. Дублированное *знание* (бизнес-правила, константы, валидация) устраняется на второй копии. Дублированная *форма* ждёт третьей.
- **YAGNI:** никаких фич, флагов и опций, которых нет в спецификации.
- **SOLID там, где окупается:** одна ответственность на модуль, зависимости с I/O передаются, а не импортируются как глобальные, маленькие интерфейсы на границах.
- **Функциональное ядро, императивная оболочка:** бизнес-правила — чистые функции без I/O, а обработчики, задачи и адаптеры делают I/O и вызывают ядро.
- **Явное лучше умного:** без метапрограммирования, скрытого глобального состояния и булевых флагов, переключающих поведение.
- **Fail fast:** валидация на краю, проверка инвариантов, ошибки не проглатываются. `catch` либо обрабатывает ошибку, либо добавляет контекст и пробрасывает дальше.

## Структура

По фичам (вертикальные срезы), а не по техническим слоям, как только модулей больше нескольких:

```text
src/
  orders/          # одна фича: routes, service, domain, repo, tests
    api.ts | routes.py
    service.ts     # use cases, оркестрирует domain и repos
    domain.ts      # чистые правила
    repo.ts        # только доступ к данным
    orders.test.ts
  shared/          # только код, используемый 2+ фичами
```

Зависимости направлены внутрь: api → service → domain. Repo внедряется в service. Контролируется `dependency-cruiser` или `import-linter` в `make check`.

## API

- **Сначала контракт:** OpenAPI или типизированные схемы маршрутов до обработчиков, типы клиента генерируются.
- Валидация каждого входа на границе схемой: zod или valibot в TypeScript, pydantic в Python.
- Единый формат ошибок RFC 9457 Problem Details (`type`, `title`, `status`, `detail`) со стабильными машиночитаемыми кодами. Стектрейсы не утекают.
- Правильные коды статусов, идемпотентные повторные POST (idempotency keys), курсорная пагинация для растущих списков.
- Версионирование только при неизбежном несовместимом изменении.

## Данные

- Миграции стандартным инструментом стека (Prisma/Drizzle, Alembic, Django), только вперёд и с ревью. Схема не меняется вне миграций.
- Только параметризованные запросы или ORM. **Никакой сборки SQL конкатенацией строк.**
- Транзакции вокруг use case с несколькими записями. Индексы — часть фичи.
- Время в UTC, деньги — целыми минорными единицами или decimal, никогда float.

## Конфигурация и секреты

- 12-factor: конфигурация из окружения, валидация схемой при старте, приложение падает, если чего-то не хватает.
- Секреты не попадают в репозиторий и логи. Локально — `.env` в `.gitignore` и закоммиченный `.env.example`. На серверах — Ansible Vault ([ansible-conventions](ansible-conventions.md)).

## Базовая безопасность

- Проверенная библиотека авторизации или встроенные средства фреймворка. **Никаких самописных сессий, JWT и хранения паролей.** Пароли — argon2id.
- Cookie сессии: `HttpOnly`, `Secure`, `SameSite=Lax` или строже. CSRF-защита для изменений с cookie-аутентификацией.
- Авторизация при каждом доступе к ресурсу (на уровне объекта).
- Rate limiting на авторизацию и дорогие эндпоинты, лимиты размера запроса, проверка загружаемых файлов по содержимому, хранение вне web root.
- Заголовки безопасности: CSP, HSTS, X-Content-Type-Options, Referrer-Policy, frame-ancestors. Строгий allowlist CORS.
- Минимальные привилегии пользователя БД, зависимости закреплены lock-файлами.

## Наблюдаемость

- Структурированные JSON-логи с request id, без персональных данных и секретов.
- `GET /healthz` (liveness) и `GET /readyz` (зависимости доступны). Оба используются smoke-тестами при деплое.
- Точки подключения трекинга ошибок; Sentry и аналоги — только если это разрешает спецификация.

## Контроль в make check

| Задача | TypeScript / Node | Python |
|---|---|---|
| Линтер и формат | `eslint` + `prettier` или `biome` | `ruff check` + `ruff format` |
| Типы | `tsc --noEmit` (strict) | `mypy --strict` или `pyright` |
| Тесты | `vitest` / `jest` | `pytest` |
| Дублирование | `jscpd` | `jscpd` |
| Мёртвый код | `knip` | `vulture` |
| Границы модулей | `dependency-cruiser` | `import-linter` |
| SAST | `semgrep --config auto` | `semgrep --config auto`, `bandit` |
| Секреты | `gitleaks detect` | `gitleaks detect` |
| Зависимости | `npm audit` / `pnpm audit`, `osv-scanner` | `pip-audit`, `osv-scanner` |

## Definition of done

Критерии приёмки покрыты тестами · `make check` зелёный · нет TODO без записи в трекере · `reuse:`-заметка написана · у публичных функций и эндпоинтов понятные имена, docstring только там, где неочевидно *зачем* · миграции включены · `.env.example` обновлён, если менялась конфигурация.
